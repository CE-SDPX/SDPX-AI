# วิศวกรซอฟต์แวร์ยุคใหม่ กับ 4 คุณสมบัติที่องค์กรมองหา

> เอกสารนี้เขียนโดยมี AI (Claude) ช่วย อาจมีส่วนที่ผิด ตกหล่น หรือเก่าไปแล้ว
> ลองเช็กกับแหล่งอ้างอิงท้ายบทก่อนเชื่อ การสงสัยสิ่งที่อ่านก็เป็นส่วนหนึ่งของวิชานี้
> ตัวเลขในกรณีตัวอย่างเป็นตัวเลขสมมติ ไม่ได้มาจากงานวิจัย

> **เชื่อมกับ loop ของวิชา:** สี่คุณสมบัตินี้บอกว่า loop ที่ดีให้อะไรกับองค์กร
> คือรับของใหม่ได้เร็ว ทำสิ่งที่มีคุณค่าจริง ไม่เผาทรัพยากรทิ้ง และไม่ล้มเมื่อโดนแรงกระแทก

| เรื่อง | ทำไมถึงสำคัญ |
|---|---|
| รู้ว่าองค์กรวัดคุณค่าของวิศวกรจากอะไรในปี 2026 | เลือกลงแรงกับสิ่งที่ถูกตั้งแต่ต้น แทนที่จะเก่งในเรื่องที่ไม่มีใครวัด |
| เรียนเทคโนโลยีใหม่ได้เร็วโดยไม่ต้องรอให้มีคนสอน | เทคโนโลยีที่ใช้ตอนเรียนจบ ไม่ใช่ตัวที่จะใช้อีก 5 ปีข้างหน้า |
| เชื่อมงานเทคนิคเข้ากับตัวเลขทางธุรกิจได้ | ข้อเสนอที่เชื่อมถึงธุรกิจได้มักถูกอนุมัติ ที่เหลือมักถูกเลื่อน |
| ประเมินต้นทุนรวมของทางเลือกทางเทคนิค | องค์กรจ่ายค่าคนแพงกว่าค่าเครื่อง ประหยัดผิดที่จึงกลายเป็นแพงกว่าเดิม |
| ออกแบบระบบให้เสียหายในวงจำกัดเมื่อมีอะไรพัง | ไม่มีระบบไหนไม่พัง มีแต่ระบบที่พังแล้วฟื้นเร็ว กับระบบที่พังแล้วจบเลย |

## ศัพท์ที่ควรรู้ก่อน

| ศัพท์ | ความหมาย |
|---|---|
| Challenge-ready | พร้อมรับโจทย์ที่ไม่เคยเจอ โดยไม่ต้องรอให้มีคนมาสอนก่อน |
| Business-centric | ตัดสินใจโดยดูคุณค่าที่เกิดกับผู้ใช้และธุรกิจ ไม่ใช่ความชอบทางเทคนิค |
| Cost-effective | ได้ผลลัพธ์ที่ต้องการ ด้วยต้นทุนรวมที่ต่ำที่สุดเท่าที่ยอมรับได้ |
| Resilience | ระบบทำงานต่อและฟื้นตัวได้เมื่อบางส่วนล้มเหลว |
| TCO | Total Cost of Ownership คือต้นทุนตลอดอายุ ไม่ใช่แค่ต้นทุนตอนสร้าง |
| Unit economics | ต้นทุนและรายได้ต่อหนึ่งหน่วยการใช้งาน เช่น ต่อ 1 คำขอ ต่อ 1 ผู้ใช้ |
| FinOps | การบริหารต้นทุนคลาวด์ให้เป็นหน้าที่ร่วมกันของทีมวิศวกรรม |
| Blast radius | ถ้าบางอย่างล้มเหลว ความเสียหายจะกว้างแค่ไหน |
| Graceful degradation | ระบบยอมลดความสามารถบางส่วน เพื่อรักษาส่วนสำคัญไว้ |
| SLI / SLO | SLI คือตัวชี้วัดระดับบริการ SLO คือเป้าหมายที่ตกลงกันไว้ |
| Error budget | ความล้มเหลวที่ยอมรับได้ในช่วงเวลาหนึ่ง ตามที่ SLO กำหนด |
| MTTR | เวลาเฉลี่ยที่ใช้กู้บริการกลับมาหลังเกิดเหตุ |
| Chaos engineering | จงใจสร้างความล้มเหลวในสภาพที่คุมได้ เพื่อพิสูจน์ว่าระบบทนได้จริง |
| Complexity budget | ความซับซ้อนที่ทีมรับไหว ถ้าใช้หมดแล้วทุกอย่างจะช้าลง |

## 1. ทำไมนิยามของ "วิศวกรที่เก่ง" ถึงเปลี่ยน

สมัยที่การเขียน code ต้องใช้แรงมาก คนที่เขียนได้เร็วและถูกคือคนที่มีค่าที่สุด
แต่ตอนนี้ขั้นตอนนั้นถูกลงเรื่อย ๆ ด้วยเครื่องมือ คลาวด์ open source และ AI
คอขวดขององค์กรจึงย้ายไปอยู่ที่อื่น

```mermaid
flowchart LR
    subgraph old["สิ่งที่หายากในอดีต"]
        O1["คนที่เขียน code ถูกและเร็ว"]
    end
    subgraph new["สิ่งที่หายากในปัจจุบัน"]
        N1["คนที่รู้ว่าควรสร้างอะไร"]
        N2["คนที่ตรวจได้ว่าของที่ได้มาถูกจริง"]
        N3["คนที่ทำให้ระบบอยู่รอดในวันที่แย่ที่สุด"]
        N4["คนที่ทำทั้งหมดนี้ด้วยต้นทุนที่คุ้ม"]
    end
    old --> new
```

สี่คุณสมบัติต่อไปนี้ไม่ใช่คำสวยหรูในประกาศรับสมัครงาน
มันคือสี่คำถามที่ผู้บริหารถามจริงตอนประเมินทีมวิศวกรรม

```mermaid
flowchart TB
    E["วิศวกรซอฟต์แวร์ยุคใหม่"]
    E --> C["Challenge-ready<br/>พร้อมทุกความท้าทาย"]
    E --> B["Business-centric<br/>ตอบโจทย์ธุรกิจจริง"]
    E --> M["Cost-effective<br/>คุ้มค่า"]
    E --> R["Highly resilient<br/>พังยาก"]
```

## 2. Challenge-ready: พร้อมทุกความท้าทาย

### 2.1 ความหมายที่แท้จริง

ไม่ได้แปลว่า "รู้ทุกเทคโนโลยี" เพราะเป็นไปไม่ได้
แต่แปลว่าเจอของที่ไม่เคยเห็นแล้วยังทำงานให้เสร็จได้ในเวลาที่ยอมรับได้

องค์กรดูจากพฤติกรรม 3 อย่าง

| พฤติกรรม | คนที่ยังไม่พร้อม | คนที่พร้อม |
|---|---|---|
| เจอ error ที่ไม่เคยเห็น | รอถามคนอื่นทันที | อ่าน error ให้จบก่อน ตั้งสมมติฐาน 2-3 ข้อ ลองเอง แล้วค่อยถามพร้อมบอกว่าลองอะไรไปแล้ว |
| ได้รับโจทย์ที่ไม่ชัด | รอให้มีคนทำให้ชัด | ไปคุยกับคนที่รู้ แล้วเขียนความเข้าใจของตัวเองส่งกลับไปให้ยืนยัน |
| ต้องใช้ technology ที่ไม่เคยใช้ | คิดว่าต้องเรียนให้ครบก่อนถึงจะเริ่มได้ | หาส่วนที่โจทย์ตอนนี้ต้องใช้ ทำ spike สั้น ๆ แล้วค่อยขยาย |

### 2.2 ฐานที่ไม่เปลี่ยน กับเปลือกที่เปลี่ยนตลอด

```mermaid
flowchart TB
    subgraph shell["เปลือก อายุ 2-5 ปี"]
        S1["framework ที่กำลังฮิต"]
        S2["cloud service เฉพาะเจ้า"]
        S3["เครื่องมือ AI รุ่นปัจจุบัน"]
    end
    subgraph core["แกน อายุหลายสิบปี"]
        C1["โครงสร้างข้อมูลและ complexity"]
        C2["การทำงานของเครือข่ายและ HTTP"]
        C3["ระบบฐานข้อมูลและ transaction"]
        C4["ระบบปฏิบัติการ process หน่วยความจำ"]
        C5["การทดสอบและการออกแบบระบบ"]
        C6["ความปลอดภัยขั้นพื้นฐาน"]
    end
    core -->|"ทำให้เรียนเปลือกใหม่ได้เร็ว"| shell
```

คนที่เข้าใจว่า HTTP ทำงานอย่างไร เรียน framework ตัวใหม่ได้ในสัปดาห์เดียว
คนที่รู้แค่วิธีใช้ framework ตัวเดิม ต้องเริ่มนับหนึ่งใหม่ทุกครั้งที่กระแสเปลี่ยน

สำหรับนักศึกษา แนะนำให้ใช้เวลากับแกนอย่างน้อยครึ่งหนึ่ง
เปลือกอาจทำให้ได้งานแรก แต่แกนทำให้ยังมีงานทำในอีก 10 ปี

### 2.3 T-shaped และวิธีสร้าง

```mermaid
flowchart TB
    W["กว้าง: รู้พอที่จะคุยกับคนอื่นรู้เรื่อง<br/>frontend · backend · database · infra · security · product"]
    W --> D["ลึก: เก่งจริงอย่างน้อย 1 เรื่อง<br/>ที่คนอื่นมาถามเราได้"]
```

ความกว้างทำให้เรามองเห็นปัญหาที่คนอื่นมองไม่เห็น เพราะปัญหาที่แพงที่สุดมักอยู่ที่รอยต่อ
ความลึกทำให้ทีมไว้ใจเรา เพราะทีมต้องการคนที่รับผิดชอบเรื่องนั้นได้จริง

### 2.4 วิธีเรียนที่ได้ผลจริง

```mermaid
flowchart LR
    P["ตั้งโจทย์ที่จับต้องได้<br/>ไม่ใช่ “อยากเรียน X”<br/>แต่ “อยากทำ Y ด้วย X”"]
    P --> B["สร้างของเล็ก ๆ ที่ใช้ได้จริง"]
    B --> BR["ทำให้มันพัง แล้วซ่อม<br/>ความเข้าใจเกิดตอนซ่อม"]
    BR --> E["อธิบายให้คนอื่นฟัง<br/>จุดที่อธิบายไม่ได้คือจุดที่ยังไม่เข้าใจ"]
    E --> P
```

> **กรณีตัวอย่าง**
> คำถามยอดนิยมในการสัมภาษณ์คือ "เล่าเรื่องที่คุณต้องเรียนอะไรใหม่เร็ว ๆ เพื่อแก้ปัญหาให้ฟังหน่อย"
> ผู้สัมภาษณ์ไม่ได้ฟังว่าเราเรียนอะไร แต่ฟังว่าเราตัดสินใจอย่างไรว่าจะเรียนแค่ไหนถึงพอ
> คนที่ตอบว่า "อ่านเอกสารทั้งหมดให้จบก่อน" กับคนที่ตอบว่า
> "หาส่วนที่จำเป็นก่อน ทำต้นแบบ 2 ชั่วโมง แล้วค่อยขยาย" ให้สัญญาณต่างกันมาก

## 3. Business-centric: ตอบโจทย์ธุรกิจจริง

### 3.1 Output ไม่เท่ากับ Outcome

```mermaid
flowchart LR
    A["Activity<br/>เขียน code 3,000 บรรทัด"] --> O["Output<br/>ปล่อย 5 feature"]
    O --> OC["Outcome<br/>ผู้ใช้จองสำเร็จเพิ่มขึ้น 12%"]
    OC --> I["Impact<br/>รายได้เพิ่ม / ต้นทุนลด"]

    A -.->|"วัดง่ายแต่แทบไม่มีความหมาย"| X["ไม่ควรใช้เป็นเป้า"]
    I -.->|"วัดยากแต่คือสิ่งที่องค์กรต้องการ"| Y["ควรใช้เป็นเป้า"]
```

หลายทีมวัดตัวเองที่กล่องซ้ายเพราะวัดง่าย
ผลคือ "ทำงานหนักมากแต่ไม่มีอะไรดีขึ้น" ซึ่งเป็นอาการที่พบบ่อยที่สุดในองค์กรขนาดกลาง

คำถามที่ควรถามก่อนเริ่มทุก feature คือ
"ถ้า feature นี้สำเร็จ ตัวเลขไหนจะขยับ และเราจะรู้ได้อย่างไรว่าขยับเพราะสิ่งนี้"
ถ้าตอบไม่ได้ แปลว่ายังไม่มีใครรู้ว่าทำไปทำไม

### 3.2 เข้าใจว่าองค์กรหาเงินอย่างไร

| ประเภทธุรกิจ | เรื่องเทคนิคที่สำคัญที่สุด |
|---|---|
| อีคอมเมิร์ซ | หน้าสินค้าและขั้นตอนชำระเงินต้องเร็วและห้ามล่ม |
| SaaS แบบสมัครสมาชิก | ความเสถียรและการรักษาผู้ใช้เดิม สำคัญกว่าฟีเจอร์ใหม่ |
| ระบบภายในองค์กร | ข้อมูลต้องถูกต้อง และตรวจสอบย้อนหลังได้ |
| แพลตฟอร์มโฆษณา | ปริมาณการประมวลผลต่อต้นทุน |
| ระบบราชการ / มหาวิทยาลัย | ต้องเชื่อถือได้ในช่วงพีค เช่น วันลงทะเบียน |

สังเกตว่าข้อกำหนดทางเทคนิคที่ถูกต้องขึ้นกับรูปแบบธุรกิจทั้งหมด
ไม่มีคำตอบสากลว่า "ต้องเร็ว" หรือ "ต้องขยายได้"

### 3.3 จัดลำดับความสำคัญเป็น

เครื่องมือที่ใช้ได้ทันที และไม่ต้องมีข้อมูลมาก

| วิธี | ใช้อย่างไร |
|---|---|
| Cost of Delay | ถามว่า "ถ้าเลื่อนสิ่งนี้ออกไป 1 เดือน เสียอะไร" งานที่เสียมากที่สุดทำก่อน |
| RICE | Reach × Impact × Confidence ÷ Effort บังคับให้เขียนความมั่นใจออกมาเป็นตัวเลข |
| MoSCoW | Must / Should / Could / Won't เหมาะกับการล็อกขอบเขตของโครงการเรียน |
| Opportunity cost | ทุกครั้งที่ตอบตกลงงานหนึ่ง ก็คือปฏิเสธงานอื่นไปด้วย |

สิ่งที่ต้องระวังที่สุดคือ "ทำทุกอย่างที่ถูกขอ"
ทีมที่ไม่เคยปฏิเสธอะไรเลย คือทีมที่ให้คนอื่นกำหนดลำดับความสำคัญแทน

### 3.4 พูดภาษาที่ผู้ฟังใช้

```mermaid
flowchart LR
    T["ภาษาเทคนิค<br/>“query นี้ทำ full table scan”"]
    U["ภาษาผู้ใช้<br/>“หน้าค้นหาโหลดนาน 4 วินาที”"]
    B["ภาษาธุรกิจ<br/>“คน 30% ออกก่อนเห็นผลลัพธ์<br/>= เสียการจองราว N ครั้งต่อวัน”"]
    T --> U --> B
```

ทักษะนี้ไม่ใช่การขายของ มันคือการทำให้คนที่มีอำนาจตัดสินใจมีข้อมูลพอจะตัดสินใจถูก
และนี่เป็นหน้าที่ของวิศวกร ไม่ใช่ของฝ่ายอื่น

> **กรณีตัวอย่าง**
> วิศวกรที่โตเร็วที่สุดในองค์กรมักไม่ใช่คนที่เขียน code เก่งที่สุด
> แต่เป็นคนที่ผู้บริหารเรียกไปนั่งด้วยตอนตัดสินใจเรื่องใหญ่
> เพราะเขาอธิบายทางเลือกทางเทคนิคเป็นผลลัพธ์ทางธุรกิจได้ โดยไม่ต้องให้ใครแปลให้

## 4. Cost-effective: คุ้มค่า

### 4.1 ต้นทุนที่มองไม่เห็นคือต้นทุนที่ใหญ่ที่สุด

```mermaid
flowchart TB
    TC["ต้นทุนรวมของทางเลือกทางเทคนิค"]
    TC --> C1["ต้นทุนสร้างครั้งแรก<br/>เห็นชัด ประเมินกันเสมอ"]
    TC --> C2["ต้นทุนดูแลตลอดอายุ<br/>มักใหญ่กว่าข้อแรกหลายเท่า"]
    TC --> C3["ต้นทุนการเรียนรู้ของคนใหม่<br/>ทุกคนที่เข้าทีมต้องจ่ายซ้ำ"]
    TC --> C4["ต้นทุนโอกาส<br/>สิ่งที่ไม่ได้ทำเพราะเวลาหมดไปกับสิ่งนี้"]
    TC --> C5["ต้นทุนความล้มเหลว<br/>ค่าเสียหายเมื่อมันพัง × ความถี่"]
    TC --> C6["ต้นทุนเครื่องและบริการ<br/>มักเล็กที่สุดในบรรดาทั้งหมด"]
```

ข้อผิดพลาดที่พบบ่อยที่สุดคือประหยัดที่กล่องล่างสุด แล้วไปจ่ายเพิ่มมหาศาลที่กล่องอื่น
เช่น เลือกเครื่องมือฟรีที่ไม่มีเอกสาร แล้วทีมเสียเวลาไปหลายสัปดาห์
ในองค์กรส่วนใหญ่ เวลาของคนแพงกว่าค่าเครื่องมาก

### 4.2 งบความซับซ้อน

ทุกทีมมี complexity budget ที่จำกัด ทุกครั้งที่เพิ่มบริการใหม่ ภาษาใหม่
หรือรูปแบบสถาปัตยกรรมใหม่ เรากำลังใช้งบก้อนนี้อยู่

| สิ่งที่เพิ่มเข้ามา | ค่าใช้จ่ายที่ตามมา ซึ่งมักไม่ถูกนับ |
|---|---|
| ภาษาใหม่ 1 ภาษา | ต้องมีคนดูแล ต้องตั้ง CI ใหม่ ต้องมี linter และ test ชุดใหม่ คนใหม่ต้องเรียนเพิ่ม |
| บริการใหม่ 1 ตัว | deploy, monitoring, alert, on-call, การจัดการเวอร์ชัน, การไล่ปัญหาข้ามระบบ |
| dependency ใหม่ 1 ตัว | ต้องอัปเดตตามเมื่อมีช่องโหว่ อาจถูกทิ้งร้าง และเพิ่มพื้นที่ให้โจมตี |
| abstraction ใหม่ 1 ชั้น | ทุกคนที่อ่าน code ต้องเข้าใจมันก่อนถึงจะแก้อะไรได้ |

หลักตัดสินคือ เพิ่มความซับซ้อนได้ถ้ามันแก้ปัญหาที่มีอยู่จริงตอนนี้
ไม่ใช่ปัญหาที่คาดว่าจะมีในอนาคต

### 4.3 รู้ต้นทุนของสิ่งที่ตัวเองสร้าง

ทักษะนี้กำลังกลายเป็นข้อกำหนดพื้นฐาน วงการเรียกว่า FinOps

สิ่งที่ควรตอบได้เกี่ยวกับระบบที่เราดูแล

- ต้นทุนต่อเดือนของระบบนี้ประมาณเท่าไร และอะไรกินมากที่สุด
- ต้นทุนต่อ 1 คำขอ หรือต่อ 1 ผู้ใช้ ประมาณเท่าไร
- ถ้าผู้ใช้เพิ่มเป็น 10 เท่า ต้นทุนจะเพิ่มเป็นกี่เท่า เพิ่มแบบเส้นตรงหรือแย่กว่านั้น
- มีทรัพยากรอะไรที่เปิดค้างไว้โดยไม่มีใครใช้บ้าง

```mermaid
flowchart LR
    Q["ต้นทุนสูงเกินไป"] --> A1["วัดก่อนว่าอะไรกินงบ<br/>อย่าเดา"]
    A1 --> A2["หา 20% ที่กินงบ 80%"]
    A2 --> A3["เลือกวิธีที่ถูกที่สุดก่อน<br/>ปิดของที่ไม่ได้ใช้ · ปรับขนาดให้พอดี · cache"]
    A3 --> A4["ถ้ายังไม่พอ ค่อยแก้ที่สถาปัตยกรรม"]
```

กับดักในยุค AI: ต้นทุนต่อคำขอของระบบที่เรียก LLM ไม่คงที่ และมักสูงกว่าที่คิด
ถ้าปล่อยให้ผู้ใช้ยิงได้ไม่จำกัดโดยไม่มีเพดาน อาจได้บิลที่ไม่คาดคิด
การนับ token และตั้งเพดานจึงเป็นงานวิศวกรรม ไม่ใช่งานบัญชี

### 4.4 คุ้มค่าไม่เท่ากับถูกที่สุด

```mermaid
flowchart LR
    U["ลงทุนน้อยเกินไป<br/>ไม่มี test ไม่มี CI<br/>เสียเวลาแก้ของพังตลอด"] --- OK["จุดที่คุ้มที่สุด"] --- O["ลงทุนมากเกินไป<br/>ทำ microservices ตั้งแต่วันแรก<br/>เสียเวลากับของที่ยังไม่ต้องใช้"]
```

ทั้งสองด้านคือความสิ้นเปลืองเหมือนกัน
การเขียน test เป็นตัวอย่างคลาสสิกของการลงทุนที่คุ้ม เพราะลดต้นทุนในกล่อง
"ค่าเสียหายเมื่อพัง" และ "ต้นทุนดูแลตลอดอายุ" ซึ่งเป็นสองกล่องที่ใหญ่ที่สุด

หนี้ทางเทคนิคก็เป็นเครื่องมือทางการเงินอย่างหนึ่ง
การกู้มาเพื่อส่งของให้ทันอาจเป็นการตัดสินใจที่ถูก ถ้ารู้ตัวว่ากู้ และมีแผนจ่ายคืน
สิ่งที่อันตรายคือหนี้ที่ไม่มีใครรู้ว่ามีอยู่

## 5. Highly Resilient: พังยาก

### 5.1 เปลี่ยนคำถามจาก "จะไม่ให้พัง" เป็น "พังแล้วจะเป็นอย่างไร"

ระบบที่ทำงานตลอดเวลา 100% ไม่มีอยู่จริง
วิศวกรรมความน่าเชื่อถือจึงไม่พยายามกำจัดความล้มเหลว แต่พยายามจำกัดผลของมัน

```mermaid
flowchart TB
    F["ความล้มเหลวเกิดขึ้นแน่นอน"]
    F --> L1["ชั้นที่ 1 ป้องกัน<br/>test · review · staging · canary"]
    L1 --> L2["ชั้นที่ 2 จำกัดวง<br/>timeout · circuit breaker · bulkhead · rate limit"]
    L2 --> L3["ชั้นที่ 3 ตรวจจับเร็ว<br/>health check · metric · alert · structured log"]
    L3 --> L4["ชั้นที่ 4 ฟื้นตัวเร็ว<br/>rollback · retry · failover · runbook"]
    L4 --> L5["ชั้นที่ 5 เรียนรู้<br/>postmortem ที่ไม่โทษคน แล้วปิดช่องด้วยระบบ"]
    L5 -.->|"ทำให้ชั้นบนแข็งขึ้น"| L1
```

ตัวชี้วัดที่บอกความจริงมากที่สุดคือ MTTR ไม่ใช่จำนวนครั้งที่ล่ม
เพราะระบบที่ล่มบ่อยแต่ฟื้นใน 2 นาที สร้างความเสียหายน้อยกว่าระบบที่ล่มปีละครั้งแต่ล่มทั้งวัน

### 5.2 Resilience ในระดับ code

| สิ่งที่ต้องมี | ถ้าไม่มีจะเกิดอะไร |
|---|---|
| Timeout ทุกการเรียกข้ามเครือข่าย | ปลายทางช้า connection ค้าง ระบบเราล่มตามทั้งที่ตัวเองไม่ผิด |
| Retry เฉพาะที่ปลอดภัย พร้อม backoff | retry รัวใส่ระบบที่กำลังพัง เท่ากับซ้ำเติมให้พังหนักกว่าเดิม |
| Idempotency | ผู้ใช้กดซ้ำ หรือ retry อัตโนมัติ แล้วได้ข้อมูลซ้ำซ้อน |
| ตรวจ input ที่ขอบระบบ | ข้อมูลผิดรูปแบบไหลลึกเข้าไปจนเสียหายที่ฐานข้อมูล |
| Fallback ที่มีความหมาย | ฟีเจอร์รองล่ม แล้วลากทั้งหน้าจอล่มตาม |
| จัดการ error โดยไม่กลืนความผิดพลาด | ระบบพังเงียบ ๆ ไม่มีใครรู้จนผู้ใช้แจ้ง |

หัวใจคือ graceful degradation ต้องแยกให้ออกว่าอะไรคือแกนที่ห้ามล้ม
และอะไรคือส่วนเสริมที่ปิดชั่วคราวได้ ระบบจองที่ส่งอีเมลไม่ได้ ยังต้องจองได้

### 5.3 Resilience ในระดับกระบวนการ

```mermaid
flowchart LR
    S["ปล่อยของทีละน้อย บ่อย ๆ"] --> S2["blast radius เล็ก"]
    S2 --> S3["หาสาเหตุง่ายเพราะเปลี่ยนไม่กี่อย่าง"]
    S3 --> S4["ย้อนกลับได้เร็ว"]
    S4 --> S5["ระบบโดยรวมมั่นคงขึ้น"]
```

นี่คือข้อค้นพบของงานวิจัย DORA ที่ขัดกับสัญชาตญาณ คือความเร็วกับความมั่นคงไปด้วยกันได้ ไม่ต้องแลกกัน
ทีมที่ปล่อยของบ่อยกว่ามักพังน้อยกว่าและฟื้นเร็วกว่า
เพราะการปล่อยก้อนใหญ่นาน ๆ ครั้ง คือการสะสมความเสี่ยงไว้ปล่อยพร้อมกัน

Chaos engineering ต่อยอดจากหลักนี้ แทนที่จะรอให้ความล้มเหลวมาเอง
ก็จงใจสร้างมันขึ้นในสภาพที่คุมได้ เช่น ปิด instance หนึ่งตัวในเวลาทำการ
เพื่อพิสูจน์ว่าสิ่งที่ออกแบบไว้ทำงานจริง ไม่ใช่แค่ทำงานในเอกสาร

### 5.4 SLO และ error budget: ทำให้ "เสถียรพอ" เป็นตัวเลข

```mermaid
flowchart TB
    SLI["SLI คือสิ่งที่วัด<br/>เช่น สัดส่วนคำขอที่สำเร็จภายใน 300 ms"]
    SLO["SLO คือเป้าหมายที่ตกลงกัน<br/>เช่น 99.9% ต่อเดือน"]
    EB["Error Budget<br/>= 0.1% ที่เหลือ ≈ 43 นาทีต่อเดือน"]
    SLI --> SLO --> EB
    EB --> D1["ยังเหลืองบ: ปล่อยของใหม่ได้ตามปกติ"]
    EB --> D2["งบหมด: หยุดปล่อยของใหม่ หันมาแก้ความเสถียรก่อน"]
```

ประโยชน์ที่แท้จริงของ error budget คือมันยุติการเถียงกันระหว่างทีมพัฒนากับทีมดูแลระบบ
ด้วยกติกาที่ตกลงไว้ล่วงหน้า แทนที่จะเถียงด้วยความรู้สึกทุกครั้งที่มีเหตุ

### 5.5 ความยืดหยุ่นของ "คน" ก็เป็นส่วนหนึ่งของระบบ

ระบบที่ทนทานแต่ต้องพึ่งคนเดียวที่รู้เรื่องทั้งหมด คือระบบที่เปราะบางที่สุด

| ความเสี่ยงด้านคน | มาตรการ |
|---|---|
| Bus factor = 1 | หมุนเวียนงาน เขียน runbook และทำให้ทุกอย่างที่ทำด้วยมือเป็น script |
| ความรู้อยู่ในหัวคนเดียว | เก็บเอกสารไว้ใน repo และใช้จริง ไม่ใช่ wiki ที่ไม่มีใครเปิด |
| on-call ที่ทรมาน | ลด alert ที่ไม่ต้องลงมือทำอะไร และตั้งเป้าลด alert ทุกไตรมาส |
| กลัวถูกตำหนิเมื่อทำพลาด | ทำ postmortem ที่ไม่โทษคน ถ้าคนกลัว จะไม่มีใครรายงานเหตุตั้งแต่เนิ่น ๆ |

> **กรณีตัวอย่าง**
> ทีมที่มีวัฒนธรรมตำหนิคน จะรู้ปัญหาช้ากว่าเสมอ
> เพราะคนจะพยายามแก้เงียบ ๆ ก่อนที่ใครจะรู้ ซึ่งเข้าใจได้
> แต่ทำให้ latency ของ loop ทั้งองค์กรยาวขึ้น ความปลอดภัยทางจิตใจจึงเป็นเรื่องวิศวกรรม

## 6. สี่ด้านนี้ขัดกันเอง และนั่นคือประเด็น

```mermaid
flowchart TB
    B["Business-centric<br/>อยากส่งของให้เร็ว"] <-->|"แลกกัน"| R["Resilient<br/>อยากตรวจให้ครบก่อนปล่อย"]
    M["Cost-effective<br/>อยากใช้ทรัพยากรน้อย"] <-->|"แลกกัน"| R
    C["Challenge-ready<br/>อยากลองของใหม่"] <-->|"แลกกัน"| M
    B <-->|"แลกกัน"| M
```

งานของวิศวกรไม่ใช่การทำให้ทั้งสี่ด้านเต็มร้อย เพราะเป็นไปไม่ได้
แต่คือการเลือกจุดสมดุลให้เหมาะกับบริบท และอธิบายเหตุผลของการเลือกนั้นได้

| สถานการณ์ | ควรเอนไปทางไหน |
|---|---|
| ต้นแบบเพื่อพิสูจน์ไอเดีย ยังไม่มีผู้ใช้จริง | ธุรกิจและความเร็ว ส่วน resilience ไว้ทีหลัง |
| ระบบชำระเงินที่มีคนใช้อยู่แล้ว | resilience มาก่อนเสมอ |
| สตาร์ตอัพที่เงินใกล้หมด | ต้นทุนและความเร็ว |
| ระบบภายในที่ใช้ปีละครั้งตอนลงทะเบียน | เน้น resilience เฉพาะช่วงพีค ช่วงที่เหลือใช้ต้นทุนต่ำ |
| โครงการเรียนที่มีเวลา 8 สัปดาห์ | ส่งของให้ครบวงจรก่อน แล้วค่อยเพิ่มความแข็งแรง |

คำตอบที่ผิดคือการไม่เลือกเลย ทีมที่พยายามทำทุกด้านให้ดีที่สุดพร้อมกัน
จะได้ของที่ช้า แพง และยังไม่แข็งแรงจริง

## 7. ประเมินตัวเอง

ให้คะแนนตัวเอง 1-5 ในแต่ละข้อ แล้วเลือกข้อที่ต่ำที่สุด 2 ข้อ มาทำงานกับมันในเทอมนี้

**Challenge-ready**
- [ ] เจอ error ที่ไม่เคยเห็น แล้วหาทางแก้เองได้ก่อนถามคนอื่น
- [ ] เรียนเครื่องมือใหม่จนใช้ทำงานจริงได้ภายในไม่กี่วัน
- [ ] รับโจทย์คลุมเครือแล้วเปลี่ยนเป็นแผนที่ลงมือทำได้
- [ ] อธิบายพื้นฐานอย่าง HTTP, transaction, index ได้โดยไม่ต้องเปิดดู

**Business-centric**
- [ ] บอกได้ว่าระบบที่ทำอยู่สร้างคุณค่าให้ใคร และวัดอย่างไร
- [ ] จัดลำดับงานโดยอ้างผลกระทบ ไม่ใช่ความชอบส่วนตัว
- [ ] ปฏิเสธหรือเลื่อนงานได้ โดยเสนอทางเลือกกลับไป
- [ ] แปลปัญหาทางเทคนิคเป็นผลทางธุรกิจได้

**Cost-effective**
- [ ] ประเมินต้นทุนรวมของทางเลือก ไม่ใช่แค่ต้นทุนตอนเริ่ม
- [ ] เลือกใช้ของสำเร็จแทนการเขียนเอง เมื่อมันคุ้มกว่า
- [ ] รู้ว่าระบบของตัวเองกินทรัพยากรตรงไหนมากที่สุด
- [ ] ไม่เพิ่มความซับซ้อนสำหรับปัญหาที่ยังไม่เกิด

**Highly resilient**
- [ ] ทุกการเรียกข้ามเครือข่ายในงานของฉันมี timeout
- [ ] ตอบได้ว่าถ้าส่วนนี้ล่ม ผู้ใช้จะเจออะไร และระบบจะทำอย่างไร
- [ ] มีวิธีย้อนกลับที่เคยทดสอบแล้ว ไม่ใช่แค่เขียนไว้
- [ ] เมื่อมีเหตุ ฉันหาสาเหตุเชิงระบบ ไม่ใช่หาว่าใครทำ

# Software Testing: ภาพรวมและหลักการ

> เอกสารนี้เขียนโดยมี AI (Claude) ช่วย อาจมีส่วนที่ผิด ตกหล่น หรือเก่าไปแล้ว
> ลองเช็กกับแหล่งอ้างอิงท้ายบทก่อนเชื่อ การสงสัยสิ่งที่อ่านก็เป็นส่วนหนึ่งของวิชานี้
> ตัวเลขในกรณีตัวอย่างและตัวอย่างประกอบเป็นตัวเลขสมมติ

> **เชื่อมกับ loop ของวิชา:** test คือขั้น Verify ที่ทำให้รันเองอัตโนมัติได้
> คุณภาพของ test จึงเป็นเพดานของคุณภาพทั้ง loop รวมถึง loop ที่มี AI agent ด้วย

## อ่านแล้วจะได้อะไร

| สิ่งที่จะทำได้ | ใช้ในงานจริงอย่างไร |
|---|---|
| รู้ว่า tester ต้องทำอะไรในแต่ละ phase ไม่ใช่แค่ตอนท้าย | งานทดสอบมีค่าที่สุดตอนที่ป้องกันปัญหา ไม่ใช่ตอนยืนยันว่ามันพังแล้ว |
| เขียนรายงาน bug ที่ dev เอาไปทำต่อได้ทันที | รายงานที่ทำซ้ำไม่ได้กินเวลาทีมมากกว่าที่ประหยัดได้หลายเท่า |
| อธิบาย defect life cycle และรู้ว่าใครปิดใบได้ | ทุกองค์กรมีระบบติดตาม bug และคาดหวังให้เราใช้เป็นตั้งแต่วันแรก |
| เลือกระดับของ test ให้ตรงกับสิ่งที่อยากรู้ | ทีมที่เขียน E2E ทุกอย่างจะได้ pipeline ที่ช้าและ flaky จนไม่มีใครเชื่อ |
| ออกแบบ test case ด้วยเทคนิคที่มีหลักการ ไม่ใช่นึกเอา | test 8 ตัวที่ออกแบบดี ครอบคลุมกว่า test 40 ตัวที่เขียนสุ่ม |
| อ่านตัวเลข coverage โดยรู้ข้อจำกัดของมัน | หลายองค์กรตั้ง KPI จาก coverage ซึ่งเล่นเกมกับตัวเลขได้ง่ายมาก |
| แยก test double 5 ชนิดและเลือกใช้ให้ถูก | ใช้ mock พร่ำเพรื่อแล้ว test จะผูกกับโครงสร้างข้างใน จน refactor ไม่ได้ |
| จัดการ flaky test อย่างเป็นระบบ | flaky test ตัวเดียวทำให้คนเลิกเชื่อทั้ง suite |
| ทดสอบระบบที่มี AI อยู่ข้างใน ซึ่งผลลัพธ์ไม่คงที่ | ทักษะนี้กำลังกลายเป็นพื้นฐานของงานสายนี้ |

## ศัพท์ที่ควรรู้ก่อน

| ศัพท์ | ความหมายในวิชานี้ |
|---|---|
| Verification | "เราสร้างของถูกวิธีไหม" คือตรงตาม spec หรือเปล่า |
| Validation | "เราสร้างของที่ถูกไหม" คือแก้ปัญหาของผู้ใช้จริงหรือเปล่า |
| SUT | System Under Test ส่วนที่กำลังถูกทดสอบ |
| Test Harness | โครงสร้างรอบ test ที่ทำให้รันซ้ำแล้วได้ผลเดิม เช่น runner, fixtures, factories, test doubles, seed data |
| Test Double | ของปลอมที่ใช้แทนของจริงระหว่าง test เป็นคำรวมของ dummy/stub/spy/mock/fake |
| Fixture | สถานะตั้งต้นที่ test ต้องการก่อนเริ่มทำงาน |
| Assertion | ประโยคที่บอกว่าผลลัพธ์ต้องเป็นอะไร ถ้าไม่ตรง test จะแดง |
| Test Oracle | แหล่งที่บอกว่าผลลัพธ์ที่ถูกต้องคืออะไร เช่น spec, AC, ระบบเดิม หรือคนที่รู้เรื่อง |
| Defect / Bug | ความไม่ตรงกันระหว่างพฤติกรรมจริงกับพฤติกรรมที่คาดหวัง |
| Severity | ความรุนแรงทางเทคนิคของ bug tester เป็นคนตัดสิน |
| Priority | ความเร่งด่วนทางธุรกิจว่าจะแก้เมื่อไร เจ้าของผลิตภัณฑ์เป็นคนตัดสิน |
| Triage | ประชุมสั้น ๆ เพื่อคัดกรอง bug ใหม่ กำหนด priority และเจ้าของ |
| Retest | ทดสอบซ้ำเฉพาะ bug ที่แจ้งว่าแก้แล้ว ว่าหายจริงไหม |
| Regression | ของที่เคยทำงานได้แล้วกลับพัง ส่วน regression testing คือการตรวจว่าไม่เกิดเรื่องนี้ |
| Entry / Exit criteria | เงื่อนไขที่ตกลงไว้ว่าเมื่อไรเริ่มทดสอบได้ และเมื่อไรถือว่าทดสอบเสร็จ |
| DRE | Defect Removal Efficiency สัดส่วน bug ที่จับได้ก่อนถึงมือผู้ใช้ |
| Flaky test | test ที่บางครั้งเขียวบางครั้งแดง ทั้งที่ code ไม่เปลี่ยน |
| Coverage | สัดส่วนของ code ที่ถูกรันระหว่าง test วัดว่ามีการรัน ไม่ได้วัดว่ามีการตรวจ |
| Mutation testing | จงใจแก้ code ให้ผิดแล้วดูว่า test จับได้ไหม ใช้วัดคุณภาพของ test |
| Test isolation | test แต่ละตัวไม่แชร์สถานะกัน จึงสลับลำดับหรือรันขนานได้ |
| Determinism | input เดิม รันกี่ครั้งก็ได้ผลเดิม |
| Shift left | ย้ายการตรวจให้เกิดเร็วขึ้นในกระบวนการ |
| Quality gate | เงื่อนไขที่ต้องผ่านก่อนงานจะไปขั้นถัดไปได้ |

## 1. ทำไมต้องทดสอบ: คำตอบที่เป็นตัวเลข

คำตอบว่า "เพื่อหา bug" ไม่ผิดแต่ยังไม่พอ เหตุผลจริงคือต้นทุนของ bug ขึ้นอยู่กับว่าเราเจอมันเมื่อไร

```mermaid
flowchart LR
    A["ตอนเขียน<br/>ต้นทุนต่ำสุด"] --> B["ตอน code review"] --> C["ตอน integrate"] --> D["ตอน QA"] --> E["ผู้ใช้เจอเอง<br/>ต้นทุนสูงสุด"]
```

เรายังไม่มีตัวเลขที่ยืนยันได้ว่าแพงขึ้นกี่เท่า ตัวคูณที่มักถูกอ้างกันมีคนโต้แย้งอยู่ แต่ทิศทางที่ว่ายิ่งเจอช้ายิ่งแก้แพงเป็นที่ยอมรับกันทั่วไป
เหตุผลไม่ได้เป็นเรื่องเทคนิคล้วน ๆ แต่เป็นเรื่องบริบทที่หายไป

- **เจอตอนเขียน** เรายังจำได้ว่าทำไมเขียนแบบนั้น แก้ได้ใน 2 นาที
- **เจอหลังผู้ใช้ใช้แล้ว** ต้องทำซ้ำให้เกิด สืบจาก log แก้ ทดสอบ deploy ฉุกเฉิน แจ้งผู้ใช้ และบางกรณีต้องแก้ข้อมูลที่เสียไปแล้ว

เรื่องนี้ตรงกับเรื่อง latency ใน loop engineering โดยตรง test ที่รันใน 2 วินาทีไม่ได้แค่เร็ว
มันย้ายจุดที่เราเจอ bug จากปลายทางมาไว้ต้นทาง

> **กรณีตัวอย่าง**
> คำถามที่ควรถามไม่ใช่ "test นี้จำเป็นไหม" แต่คือ
> "ถ้าตรงนี้พัง เราอยากรู้ตอนไหน และตอนนั้นจะแก้ยากแค่ไหน"
> ส่วนของระบบที่พังแล้วเจ็บมากควรมี test ที่แน่นกว่า ส่วนที่พังแล้วแค่รำคาญก็ไม่ต้องลงแรงมาก

## 2. หน้าที่ของ Tester ในแต่ละ phase

ในทีมสมัยใหม่ คำว่า "tester" ไม่ได้แปลว่าต้องมีคนตำแหน่งนี้แยกออกมา
หลายทีมให้ developer สลับกันทำหน้าที่นี้ และในวิชานี้ทุกคนต้องทำเป็นด้วย
สิ่งที่สำคัญไม่ใช่ตำแหน่ง แต่คือต้องมีคนที่รับหน้าที่ถามว่า "เรารู้ได้อย่างไรว่ามันถูก"

### 2.1 ความเข้าใจผิดที่ต้องแก้ก่อน

> ความเข้าใจผิด: "tester คือคนที่มาไล่กดหาที่พังหลังจาก dev เขียนเสร็จ"

ถ้า tester เข้ามาแค่ตอนท้าย งานของเขาจะเหลือแค่การยืนยันว่าความเสียหายเกิดขึ้นแล้ว
คุณค่าสูงสุดของ tester คือการป้องกันไม่ให้ bug เกิด ซึ่งต้องเข้ามาตั้งแต่ตอนคุย requirement

```mermaid
flowchart LR
    subgraph late["แบบที่ไม่ช่วย: tester เข้าตอนท้าย"]
        L1["requirement คลุมเครือ"] --> L2["dev เดาความหมาย"] --> L3["tester เจอว่าเข้าใจไม่ตรงกัน"] --> L4["แก้ทั้ง design และ code"]
    end
    subgraph early["แบบที่ช่วย: tester เข้าตั้งแต่ต้น"]
        E1["tester ถามใน requirement review<br/>“ถ้าจองคาบเดียวกันพร้อมกัน 2 คน จะเกิดอะไร”"] --> E2["ทีมตอบไม่ได้<br/>แปลว่าเจอ requirement ที่หายไป"] --> E3["ตกลงกันก่อนเขียน code"]
    end
```

คำถามเดียวในห้อง requirement review อาจมีค่าเท่ากับการเจอ bug หลายสิบตัวหลัง deploy
เพราะมันตัดปัญหาตั้งแต่ต้นทาง

### 2.2 V-Model: แต่ละ phase คู่กับการทดสอบระดับไหน

```mermaid
flowchart TB
    R["Requirement<br/>ความต้องการ"] --> D["System Design<br/>สถาปัตยกรรม"]
    D --> DD["Detailed Design<br/>โมดูล"]
    DD --> C["Coding"]
    C --> UT["Unit Test"]
    UT --> IT["Integration Test"]
    IT --> ST["System Test"]
    ST --> AT["Acceptance Test"]

    R -.->|"เตรียม test ระดับนี้ตั้งแต่ phase นี้"| AT
    D -.->|"เตรียมไว้ล่วงหน้า"| ST
    DD -.->|"เตรียมไว้ล่วงหน้า"| IT
    C -.->|"เตรียมไว้ล่วงหน้า"| UT
```

ใจความของ V-Model ไม่ใช่ลำดับขั้นแบบ waterfall แต่คือเส้นประ
การทดสอบแต่ละระดับควรถูกออกแบบตั้งแต่ phase ฝั่งซ้ายที่คู่กัน ไม่ใช่มาคิดตอนถึงคิว
ทีมที่ทำงานแบบ agile ก็ใช้หลักนี้ได้ แต่วงจรจะหมุนซ้ำทุก sprint หรือทุก bolt

### 2.3 หน้าที่ของ tester ทีละ phase

| Phase | tester ทำอะไร | ส่งมอบอะไร | คำถามหลักที่ถือติดตัว |
|---|---|---|---|
| 1. Requirement / Analysis | ทบทวน user story และ AC หา requirement ที่กำกวมหรือขัดแย้ง ตรวจว่าทดสอบได้จริงไหม เสนอ AC เพิ่ม | รายการคำถามที่ยังตอบไม่ได้ AC ที่แก้แล้ว | "ข้อนี้จะพิสูจน์ว่าผ่านได้อย่างไร" |
| 2. Design | ทบทวน C4/ER diagram หาจุดที่ทดสอบยาก ขอ hook สำหรับทดสอบ เช่น seed endpoint ระบุ risk ของแต่ละส่วน | บันทึกความเสี่ยงเชิงทดสอบ ข้อกำหนดเรื่อง testability | "ถ้าส่วนนี้พังเงียบ ๆ เราจะรู้ได้อย่างไร" |
| 3. Test Planning | จัดลำดับตามความเสี่ยง กำหนดว่าจะทดสอบและไม่ทดสอบอะไร กำหนด entry/exit criteria เตรียม environment และข้อมูล | test plan ฉบับย่อ นิยามของ "พร้อมทดสอบ" และ "ทดสอบเสร็จ" | "เวลามีจำกัด ควรใช้กับส่วนไหนก่อน" |
| 4. Test Design & Implementation | เขียน test case ด้วยเทคนิคในหัวข้อ 4 เตรียม test data สร้าง test harness และ automation | test case, fixture/seed, automated test | "test นี้จะแดงเมื่อไร ถ้าไม่เคยแดงเลยแปลว่าอะไร" |
| 5. Development | ทำงานคู่กับ dev, review unit test ของ dev, ทดสอบทีละ bolt ที่เสร็จ ไม่รอจนครบทั้ง feature | feedback รายวัน bug ที่พบเร็ว | "ส่วนนี้ integrate กับของเดิมแล้วยังโอเคไหม" |
| 6. Test Execution | รัน test ตามแผน ทำ exploratory testing บันทึกผล รายงาน bug ทดสอบซ้ำหลังแก้ (retest) และทำ regression | รายงานผลการทดสอบ bug ที่มีหลักฐานครบ | "อาการนี้ทำซ้ำได้เสถียรหรือยัง" |
| 7. Release / Deploy | ตัดสินร่วมกันว่าพร้อมปล่อยไหม โดยอ้าง exit criteria ทำ smoke test หลัง deploy จริง ยืนยันแผน rollback | สรุปสถานะคุณภาพและคำแนะนำ go / no-go | "ถ้าปล่อยตอนนี้ ความเสี่ยงที่เหลือคืออะไร" |
| 8. Production / Operations | เฝ้า log และ metric สืบ bug ที่ผู้ใช้แจ้ง แปลง bug ที่หลุดออกไปเป็น test ถาวร | test ที่กันไม่ให้ bug เดิมกลับมา บทเรียน | "ทำไม suite ของเราถึงปล่อยตัวนี้ผ่าน" |
| 9. Test Completion / Retrospective | สรุปตัวเลข เก็บ test ที่ยังมีค่า ทิ้งที่หมดอายุ ถอดบทเรียนเข้ากระบวนการ | รายงานปิดรอบ การปรับปรุงกระบวนการ | "รอบหน้าจะจับได้เร็วขึ้นตรงไหน" |

แถวที่ 8 คือแถวที่แยกทีมที่เก่งออกจากทีมทั่วไป ทุก bug ที่หลุดถึงผู้ใช้ไม่ได้จบแค่การแก้
แต่ต้องจบที่คำถามว่าทำไม loop ของเราไม่จับมัน และคำตอบต้องกลายเป็น test ใหม่เสมอ

> **กรณีตัวอย่าง**
> ในทีมที่ทำงานเป็น sprint หรือ bolt สั้น ๆ ทั้ง 9 phase นี้ไม่ได้เรียงเป็นเส้นตรง
> แต่หมุนครบทุกรอบภายในไม่กี่วัน สิ่งที่ไม่เปลี่ยนคือลำดับของคำถาม
> เราต้องรู้ก่อนว่า "ถูกคืออะไร" ถึงจะทดสอบได้ ไม่ว่ารอบจะยาวหรือสั้น

### 2.4 Entry / Exit Criteria: เส้นที่ต้องตกลงกันล่วงหน้า

ความขัดแย้งระหว่าง dev กับ tester เกือบทั้งหมดมาจากการไม่ได้ตกลงสองเส้นนี้ไว้ก่อน

| | เงื่อนไข |
|---|---|
| Entry: พร้อมให้ทดสอบเมื่อไร | build ขึ้น staging แล้ว, smoke test ผ่าน, unit test เขียวใน CI, มี test data พร้อม, มีคำอธิบายว่าเปลี่ยนอะไรบ้าง |
| Exit: ถือว่าทดสอบเสร็จเมื่อไร | test case ที่วางไว้รันครบ, ไม่มี bug ระดับ Critical/High ค้าง, bug ที่เหลือมีเจ้าของและถูกยอมรับอย่างเป็นทางการ, regression suite เขียว, บันทึกผลแล้ว |

exit criteria ไม่ได้แปลว่า "ไม่มี bug เหลือเลย" เพราะเป็นไปไม่ได้
แต่แปลว่า bug ที่เหลือถูกมองเห็น ถูกประเมิน และมีคนตัดสินใจรับไว้อย่างรู้ตัว

## 3. ระดับของการทดสอบ

```mermaid
flowchart TB
    U["Unit Test<br/>ฟังก์ชัน/คลาสเดียว แยกจากของอื่น<br/>เร็วระดับมิลลิวินาที"]
    I["Integration Test<br/>หลายส่วนทำงานร่วมกัน<br/>เช่น service + database จริง"]
    S["System Test<br/>ทั้งระบบทำงานร่วมกันในสภาพใกล้ production"]
    A["Acceptance / E2E Test<br/>ผู้ใช้ทำงานให้สำเร็จได้หรือไม่"]

    U --> I --> S --> A
```

แต่ละระดับตอบคำถามคนละข้อ และใช้แทนกันไม่ได้

| ระดับ | ตอบคำถามว่า | จับ bug ประเภทไหน | จับไม่ได้ |
|---|---|---|---|
| Unit | ตรรกะข้างในถูกไหม | คำนวณผิด, เงื่อนไขขอบผิด | ประกอบกันแล้วไม่ทำงาน |
| Integration | ประกอบกันแล้วคุยกันรู้เรื่องไหม | schema ไม่ตรง, transaction, query ผิด | ผู้ใช้ใช้ไม่ได้เพราะปุ่มหาย |
| System | ระบบในสภาพจริงยังทำงานไหม | config, network, environment | ของที่ถูกทุกอย่างแต่ไม่ใช่สิ่งที่ผู้ใช้ต้องการ |
| Acceptance | ผู้ใช้ทำงานสำเร็จไหม | flow ขาด, UX พัง | รายละเอียดตรรกะลึก ๆ |

### รูปทรงของ suite: Pyramid, Trophy และ Ice Cream Cone

```mermaid
flowchart TB
    subgraph pyr["แบบที่ช่วย: Test Pyramid"]
        P3["E2E: น้อย ช้า แพง"]
        P2["Integration: ปานกลาง"]
        P1["Unit: เยอะ เร็ว ถูก"]
        P1 --> P2 --> P3
    end
    subgraph cone["แบบที่ไม่ช่วย: Ice Cream Cone"]
        C3["Manual test: เยอะที่สุด"]
        C2["E2E: เยอะ"]
        C1["Unit: แทบไม่มี"]
        C1 --> C2 --> C3
    end
```

Ice cream cone คือรูปทรงที่เกิดขึ้นเองถ้าไม่มีใครออกแบบ เพราะการทดสอบด้วยมือให้ความมั่นใจได้ทันที
โดยไม่ต้องลงทุนอะไร ปัญหาคือมันไม่สะสม สัปดาห์หน้าต้องทำใหม่ทั้งหมด

สำหรับงานที่มีหน้าจอเยอะและตรรกะน้อย เช่น web app ทั่วไป รูปทรงที่เหมาะกว่าคือสิ่งที่ Kent C. Dodds เรียกว่า
Testing Trophy ซึ่งให้น้ำหนักกับ integration มากที่สุด
เพราะ bug ส่วนใหญ่ของงานแบบนี้ไม่ได้อยู่ในตรรกะเดี่ยว ๆ แต่อยู่ตรงรอยต่อ

ข้อสรุปที่ใช้ได้จริงคือ รูปทรงที่ถูกคือรูปทรงที่ทำให้ suite ทั้งชุดรันจบเร็วพอที่จะรันทุกครั้งที่แก้ code
และเชื่อผลได้ทุกครั้ง

## 4. เทคนิคออกแบบ test case

ถ้าเราแค่นึกว่า "น่าจะทดสอบอะไร" test จะกองอยู่ที่ happy path
เทคนิคด้านล่างเป็นมาตรฐานที่สอนใน ISTQB Foundation Level และเอาไปใช้ได้ทันที

### 4.1 Equivalence Partitioning: แบ่งกลุ่มค่าที่ให้ผลเหมือนกัน

ถ้าระบบรับอายุ 18-65 การทดสอบ 20, 21, 22, 23 ไม่ได้ให้ข้อมูลเพิ่ม เพราะอยู่กลุ่มเดียวกัน

```mermaid
flowchart LR
    A["< 18<br/>ปฏิเสธ"] --- B["18-65<br/>รับ"] --- C["> 65<br/>ปฏิเสธ"]
```

เลือกตัวแทนกลุ่มละ 1 ค่า ก็เหลือ 3 test แทน 40 test

### 4.2 Boundary Value Analysis: bug อยู่ตรงขอบ

bug ส่วนใหญ่เกิดจาก `<` ที่ควรเป็น `<=` เราจึงทดสอบที่ขอบและรอบ ๆ ขอบ

สำหรับช่วง 18-65 ให้ทดสอบ 17, 18, 19 และ 64, 65, 66

รวมสองเทคนิคเข้าด้วยกันได้ test 6-8 ตัวที่ครอบคลุมกว่า test 40 ตัวที่เขียนสุ่ม

### 4.3 Decision Table: เมื่อเงื่อนไขหลายตัวมาเจอกัน

| # | เป็นสมาชิก | ยอดซื้อ > 1000 | มีคูปอง | ผลลัพธ์ที่คาดหวัง |
|---|---|---|---|---|
| 1 | ใช่ | ใช่ | ใช่ | ลด 20% |
| 2 | ใช่ | ใช่ | ไม่ | ลด 15% |
| 3 | ใช่ | ไม่ | ใช่ | ลด 10% |
| 4 | ไม่ | ใช่ | ใช่ | ลด 5% |
| 5 | ไม่ | ไม่ | ไม่ | ไม่ลด |

ประโยชน์ที่มากกว่าการได้ test case คือมันทำให้เจอช่องที่ spec ไม่ได้บอกไว้
ระหว่างทำตารางมักพบว่ามีบางแถวที่ไม่มีใครในทีมตอบได้ว่าผลควรเป็นอะไร
นั่นคือ requirement ที่หายไป และควรถามก่อนเขียน code

### 4.4 State Transition: เมื่อลำดับมีความหมาย

```mermaid
stateDiagram-v2
    [*] --> Draft
    Draft --> Submitted: submit
    Submitted --> Approved: approve
    Submitted --> Draft: reject
    Approved --> Cancelled: cancel
    Cancelled --> [*]
    Approved --> [*]
```

test ที่ต้องมีไม่ใช่แค่เส้นทางปกติ แต่รวมถึงการเปลี่ยนสถานะที่ต้องถูกปฏิเสธ
เช่น ยกเลิกใบที่ยังเป็น Draft หรืออนุมัติใบที่ถูกยกเลิกไปแล้ว
ช่องโหว่ด้าน business logic ส่วนใหญ่ซ่อนอยู่ตรงนี้

### 4.5 Pairwise Testing: เมื่อการรวมกันเยอะเกินไป

ระบบที่มี 5 ตัวเลือก ตัวละ 4 ค่า มี 1,024 แบบที่รวมกันได้ ทดสอบครบไม่ไหว
แต่ถ้าออกแบบให้ทุกคู่ของค่าปรากฏอย่างน้อยหนึ่งครั้ง จะเหลือเพียงไม่กี่สิบกรณี
และครอบคลุม bug ส่วนใหญ่ เพราะ bug ที่ต้องใช้ตัวแปร 3 ตัวขึ้นไปพร้อมกันจึงจะเกิดนั้นพบได้น้อย

## 5. Coverage: สิ่งที่มันบอก และสิ่งที่มันไม่บอก

```python
def divide(a, b):
    return a / b

# test นี้ให้ statement coverage 100%
def test_divide():
    divide(10, 2)     # ไม่มี assert เลยแม้แต่ตัวเดียว
```

test ข้างบนได้ coverage 100% แต่จับอะไรไม่ได้เลย แม้เปลี่ยนเป็น `a * b` ก็ยังเขียว

| ชนิดของ coverage | วัดอะไร | ยังพลาดอะไร |
|---|---|---|
| Statement | บรรทัดถูกรันหรือยัง | ไม่รู้ว่ามีการตรวจผลหรือไม่ |
| Branch | ทุกกิ่ง if/else ถูกรันครบไหม | ไม่รู้ว่าเงื่อนไขย่อยถูกทดสอบครบ |
| Condition | เงื่อนไขย่อยแต่ละตัวเป็นทั้ง true และ false | ยังไม่ครอบคลุมทุกการรวมกัน |
| Path | ทุกเส้นทางถูกเดินครบไหม | เพิ่มแบบทวีคูณ ทำครบไม่ไหวในทางปฏิบัติ |

Coverage ใช้เป็นตัวชี้วัดเชิงลบได้ดี ส่วนที่ coverage เป็น 0% แปลว่าไม่มีอะไรตรวจแน่นอน
แต่ 90% ไม่ได้แปลว่าปลอดภัย 90% และเมื่อไรที่มันกลายเป็น KPI ก็จะมีคนเล่นเกมกับมันทันที
(Goodhart's Law อีกแล้ว)

### Mutation Testing: วัดคุณภาพของ test แทน

แนวคิดคือจงใจแก้ code ให้ผิดทีละจุด แล้วดูว่า test แดงไหม

```mermaid
flowchart LR
    S["code ต้นฉบับ"] --> M["สร้าง mutant<br/>เปลี่ยน > เป็น >=<br/>เปลี่ยน + เป็น -<br/>ลบบรรทัด"]
    M --> T["รัน test"]
    T -->|"test แดง"| K["killed<br/>test ทำงาน"]
    T -->|"test เขียว"| SV["survived<br/>ไม่มีอะไรตรวจตรงนี้"]
```

Mutation score คือ mutant ที่ถูกฆ่า หารด้วย mutant ทั้งหมด โกงยากกว่า coverage มาก
เพราะจะได้คะแนนสูง test ต้องมี assertion ที่มีความหมายจริง ๆ
เครื่องมือที่ใช้ได้ คือ `mutmut`/`cosmic-ray` สำหรับ Python และ Stryker สำหรับ JS/TS

## 6. Test Double: ของปลอม 5 ชนิด

คำศัพท์ชุดนี้มาจาก *xUnit Test Patterns* ของ Gerard Meszaros
คนส่วนใหญ่เรียกทุกอย่างว่า "mock" ทำให้คุยกันคนละเรื่อง

| ชนิด | ทำอะไร | ใช้เมื่อไร |
|---|---|---|
| Dummy | ส่งไปให้ครบพารามิเตอร์ ไม่ถูกใช้จริง | ต้องใส่ค่าแต่ค่านั้นไม่เกี่ยว |
| Stub | คืนค่าที่กำหนดไว้ล่วงหน้า | ต้องการให้ dependency ตอบแบบเจาะจง |
| Spy | เป็น stub ที่จำว่าถูกเรียกอย่างไรบ้าง | อยากตรวจว่ามีการเรียกจริง เช่น ส่งอีเมล |
| Mock | ตั้งความคาดหวังไว้ล่วงหน้า และ fail ถ้าไม่เป็นไปตามนั้น | ตรวจพฤติกรรมการเรียกเป็นหลัก |
| Fake | ของจริงเวอร์ชันย่อที่ทำงานได้ เช่น in-memory repository | อยากได้ของที่ทำงานจริงแต่เร็ว |

```mermaid
flowchart TD
    Q1{"ต้องการอะไร"}
    Q1 -->|"แค่ให้พารามิเตอร์ครบ"| D["Dummy"]
    Q1 -->|"ให้ค่ากลับมาแบบกำหนดได้"| ST["Stub"]
    Q1 -->|"ตรวจว่าถูกเรียกไหม"| SP["Spy"]
    Q1 -->|"บังคับว่าต้องถูกเรียกแบบนี้เท่านั้น"| MO["Mock"]
    Q1 -->|"อยากได้ของที่ทำงานได้จริงแต่เบา"| FA["Fake"]
```

### Over-mocking: กับดักที่พบบ่อยที่สุด

เมื่อ test เต็มไปด้วย mock สิ่งที่มันตรวจจะกลายเป็นโครงสร้างภายในของ code
ไม่ใช่พฤติกรรมที่ผู้ใช้สนใจ ผลคือ refactor ทีไร test แดงทุกที ทั้งที่พฤติกรรมไม่เปลี่ยนเลย
test แบบนี้จากที่ควรเป็นตาข่ายนิรภัย กลายเป็นโซ่ตรวน

หลักตัดสินคือ mock เฉพาะสิ่งที่อยู่ข้ามขอบเขตที่เราควบคุมไม่ได้
เช่น network, เวลา, ระบบไฟล์, บริการภายนอก, การสุ่ม
ส่วนตรรกะภายในของเราเอง ให้ใช้ของจริง

> **กรณีตัวอย่าง**
> `time` กับ `random` คือสองสิ่งที่ทำให้ test flaky มากที่สุดในระบบจริง
> ทีมที่ทำถูกจะ inject ทั้งสองอย่างเข้าไปตั้งแต่ต้น ไม่ใช่เรียก `Date.now()` กลางฟังก์ชัน
> การออกแบบให้ test ได้กับการออกแบบให้ดี มักเป็นเรื่องเดียวกัน

## 7. TDD และ BDD

### TDD: Red, Green, Refactor

```mermaid
flowchart LR
    R["Red<br/>เขียน test ที่ยังไม่ผ่าน"] --> G["Green<br/>เขียน code ให้ผ่านแบบง่ายที่สุด"] --> RF["Refactor<br/>จัดระเบียบโดย test ต้องเขียวตลอด"] --> R
```

คุณค่าจริงของ TDD ไม่ใช่การได้ test แต่คือมันบังคับให้เราออกแบบ interface ก่อนลงมือ
การเขียน test ก่อนคือการเขียนว่าเราจะเรียกใช้ของสิ่งนี้อย่างไร ซึ่งก็คือการออกแบบ

ขั้น Red มีหน้าที่สำคัญที่คนข้ามบ่อย คือมันพิสูจน์ว่า test ตัวนี้จับอะไรได้จริง
test ที่ไม่เคยเห็นเป็นสีแดง คือ test ที่เรายังไม่รู้ว่าใช้งานได้หรือเปล่า

TDD กับ AI agent: เมื่อ agent เขียน code ได้เร็วมาก การเขียน test ก่อนก็คือการให้เป้าหมายที่วัดได้กับมัน
agent จะมีสัญญาณชัดว่าเสร็จหรือยัง แทนที่จะต้องเดาว่ามนุษย์พอใจหรือยัง

### BDD: ภาษาที่คนไม่ใช่ programmer อ่านได้

```gherkin
Feature: จองห้องประชุม

  Scenario: จองห้องว่างสำเร็จ
    Given ห้อง "A101" ว่างในวันที่ 2026-08-10 เวลา 09:00-10:00
    When ผู้ใช้ "somchai" จองห้อง "A101" ในช่วงเวลานั้น
    Then การจองถูกบันทึกด้วยสถานะ "confirmed"
    And ผู้ใช้เห็นการจองในหน้ารายการของตัวเอง
```

ประโยชน์ไม่ได้อยู่ที่ syntax แต่อยู่ที่มันบังคับให้เราเขียนเกณฑ์ยอมรับให้ชัดก่อนเขียน code
รูปแบบ Given/When/Then เป็นโครงเดียวกับ AAA (Arrange / Act / Assert) ในระดับ unit

## 8. Flaky Test: ศัตรูอันดับหนึ่งของความเชื่อถือ

test ที่เขียวบ้างแดงบ้างโดย code ไม่เปลี่ยน ทำลายทั้ง suite
เพราะเมื่อคนเริ่มชินกับการ "รันใหม่อีกทีเดี๋ยวก็เขียว" test แดงที่เป็นของจริงก็จะถูกมองข้ามไปด้วย

| สาเหตุ | อาการ | วิธีแก้ |
|---|---|---|
| แชร์สถานะระหว่าง test | สลับลำดับแล้วแดง | ให้แต่ละ test สร้างและเก็บกวาดข้อมูลของตัวเอง |
| พึ่งเวลาจริง | แดงตอนข้ามวัน หรือตอนเที่ยงคืน | inject clock แล้วตรึงเวลาใน test |
| รอด้วย sleep | แดงเมื่อเครื่อง CI ช้ากว่าปกติ | ใช้ assertion ที่รอจนกว่าเงื่อนไขจะเป็นจริง |
| ลำดับแบบขนาน | รันขนานแล้วแดง | แยก database/schema ต่อ worker |
| พึ่งบริการภายนอก | แดงเมื่อเน็ตช้า | ใช้ test double หรือ container ของตัวเอง |
| ไม่ deterministic | แดงแบบสุ่ม | ตรึง seed ของการสุ่ม |

นโยบายที่ทีมที่ทำถูกใช้กัน

```mermaid
flowchart LR
    F["พบ flaky test"] --> Q["quarantine<br/>ย้ายออกจาก gate หลักทันที"] --> T["เปิด ticket มีเจ้าของและกำหนดวัน"] --> FX["แก้ที่ต้นเหตุ"] --> B["นำกลับเข้า suite"]
```

สิ่งที่ห้ามทำคือใส่ retry ทับไว้แล้วเดินหน้าต่อ retry แค่ซ่อนอาการ
แต่บ่อยครั้งอาการนั้นคือ race condition จริงที่ผู้ใช้จะเจอทีหลัง

## 9. เจอ bug แล้วต้องทำอะไร และ Defect Life Cycle

การเจอ bug เป็นแค่จุดเริ่ม ว่ามันจะถูกแก้จริงหรือหายไปเฉย ๆ
ขึ้นอยู่กับสิ่งที่เกิดขึ้นใน 15 นาทีถัดมา

### 9.1 ลำดับการทำงานเมื่อเจอ bug

```mermaid
flowchart TD
    F["เจออาการผิดปกติ"] --> R1["1. ทำซ้ำให้ได้<br/>ลดขั้นตอนให้เหลือน้อยที่สุดที่ยังเกิด"]
    R1 -->|"ทำซ้ำไม่ได้"| NR["บันทึกไว้พร้อมหลักฐานเท่าที่มี<br/>อย่าทิ้ง ตั้งเป็นข้อสังเกตที่ต้องเฝ้า"]
    R1 -->|"ทำซ้ำได้"| R2["2. ตรวจว่ามีคนรายงานแล้วหรือยัง"]
    R2 -->|"มีแล้ว"| DUP["เพิ่มหลักฐานลงใบเดิม<br/>ไม่เปิดใบใหม่"]
    R2 -->|"ยังไม่มี"| R3["3. หาขอบเขต<br/>เกิดทุก browser ไหม ทุก role ไหม<br/>เกิดตั้งแต่ commit ไหน"]
    R3 --> R4["4. เก็บหลักฐาน<br/>ขั้นตอน · ผลที่คาด vs ผลจริง · log + correlation id<br/>screenshot/trace · version/commit · environment"]
    R4 --> R5["5. จัด severity และ priority"]
    R5 --> R6["6. เขียนรายงานตามแม่แบบ"]
    R6 --> R7{"เป็นระดับ Critical<br/>บน production ไหม"}
    R7 -->|"ใช่"| ESC["แจ้งทันทีผ่านช่องทางด่วน<br/>ไม่รอรอบ triage"]
    R7 -->|"ไม่"| TRI["เข้าคิว triage ตามปกติ"]
```

ขั้นที่ 1 คือขั้นที่คนข้ามบ่อยที่สุดและแพงที่สุด
รายงานที่บอกแค่ "กดแล้วพัง" โดยไม่มีขั้นตอนที่ทำซ้ำได้ จะกินเวลา dev มากกว่าที่ tester ประหยัดได้หลายเท่า

วิธีลดขั้นตอนคือตัดออกทีละอย่างแล้วลองใหม่ ถ้ายังเกิดอยู่ แปลว่าขั้นตอนที่ตัดไม่เกี่ยว
สุดท้ายเราจะได้ขั้นตอนที่สั้นที่สุดที่ยังทำให้เกิด ซึ่งมักชี้ไปที่สาเหตุได้เอง

> **กรณีตัวอย่าง**
> `"cannot reproduce"` ไม่ใช่คำตอบ แต่เป็นสัญญาณว่ากระบวนการมีรู
> อาจเพราะ log ไม่พอ ไม่ได้บันทึกเวอร์ชัน หรือ environment ต่างกัน
> ทีมที่ทำถูกจะมองใบที่ปิดด้วยเหตุผลนี้เป็นปัญหาของระบบสังเกตการณ์ ไม่ใช่ความผิดของผู้รายงาน

### 9.3 Severity ต่างจาก Priority

สองคำนี้ถูกใช้สลับกันบ่อยที่สุดในวงการ แต่เป็นคนละเรื่องกัน

- **Severity** คือความรุนแรงทางเทคนิค ผู้รายงานหรือ tester เป็นคนตัดสิน
- **Priority** คือความเร่งด่วนทางธุรกิจ เจ้าของผลิตภัณฑ์เป็นคนตัดสิน

| | Priority สูง | Priority ต่ำ |
|---|---|---|
| **Severity สูง** | ชำระเงินแล้วเงินหักแต่ไม่ได้สินค้า: แก้ทันที | ระบบล่มเมื่อใช้ browser ที่เลิกสนับสนุนแล้ว: เข้าคิวปกติ |
| **Severity ต่ำ** | ชื่อบริษัทสะกดผิดบนหน้าแรก: แก้วันนี้ แม้ไม่กระทบการทำงาน | ข้อความ tooltip ในหน้า admin เยื้อง 2px: ทำเมื่อว่าง |

ช่อง Severity ต่ำ / Priority สูง คือช่องที่พิสูจน์ว่าสองคำนี้ไม่ใช่สิ่งเดียวกัน
และเป็นเหตุผลที่ tester ไม่ควรตัดสิน priority เพียงลำพัง

เกณฑ์ severity ที่ใช้ได้จริง

| ระดับ | เกณฑ์ |
|---|---|
| Critical | ระบบใช้ไม่ได้ / ข้อมูลเสียหายถาวร / ข้อมูลรั่ว / ไม่มีทางเลี่ยง |
| High | ฟังก์ชันหลักใช้ไม่ได้ แต่มีทางเลี่ยงที่ยุ่งยาก |
| Medium | ฟังก์ชันรองผิดพลาด หรือฟังก์ชันหลักผิดในกรณีเฉพาะ |
| Low | ปัญหาด้านความสวยงามหรือข้อความ ไม่กระทบการใช้งาน |

### 9.4 Defect Life Cycle

```mermaid

    [*] --> New: tester รายงาน
    New --> Assigned: triage มอบหมายเจ้าของ
    New --> Rejected: ไม่ใช่ bug / ทำงานตามที่ออกแบบ
    New --> Duplicate: ซ้ำกับใบที่มีอยู่
    New --> Deferred: ยอมรับว่าเป็น bug แต่ยังไม่แก้ตอนนี้

    Assigned --> InProgress: dev เริ่มแก้
    InProgress --> Fixed: แก้แล้ว + มี test คุ้มครอง
    InProgress --> CannotReproduce: ทำซ้ำไม่ได้

    CannotReproduce --> New: ผู้รายงานให้ข้อมูลเพิ่ม
    CannotReproduce --> Closed: ตกลงร่วมกันว่าปิด

    Fixed --> ReadyForTest: deploy ขึ้น environment ทดสอบ
    ReadyForTest --> Retest: tester ทดสอบซ้ำ
    Retest --> Verified: อาการหายและ regression เขียว
    Retest --> Reopened: ยังเกิดอยู่ / แก้แล้วพังที่อื่น (ในรอบเดียวกัน)

    Reopened --> Assigned
    Verified --> Closed: ปิดโดยผู้รายงาน

    Duplicate --> Closed

    ReFound --> Reopened: สาเหตุรากเดิม + ยังไม่ข้าม release
    ReFound --> LinkedNew: คนละสาเหตุราก หรือข้าม release ไปแล้ว
    LinkedNew --> [*]: เปิดใบใหม่ที่ลิงก์กลับใบเดิม แล้วเริ่มวงจรใหม่ที่ New

    Closed --> [*]: ไม่กลับมาอีก

    note right of Closed

    end note
```

diagram นี้ต่างจากแบบพื้นฐานตรงที่ `Closed` ไม่ใช่สถานะสุดท้ายอย่างเดียวอีกแล้ว
และมีจุดตัดสินคั่นก่อนเสมอ ไม่ได้ลากเส้น `Closed --> Reopened` ตรง ๆ
เพราะถ้า reopen อัตโนมัติทุกครั้งที่เจออาการซ้ำ รายงานคุณภาพของ release ที่ปิดไปแล้วจะเพี้ยน

```mermaid

    participant B as Bug Tracker
    participant P as Product Owner
    participant D as Developer
    participant CI as CI/CD

    D->>D: แก้ code จน test เขียว
    D->>B: Fixed + อ้าง commit
    D->>CI: push
    CI->>CI: unit + E2E + regression
```

ขั้นที่ 7 คือเขียน test ที่แดงเพราะ bug นี้ก่อนแก้ ขั้นนี้ทำให้วงจรเป็นการเพิ่ม coverage ให้ loop จริง ๆ
ไม่ใช่แค่ซ่อมอาการ ถ้า test ตัวนั้นไม่เคยแดงมาก่อน แปลว่ามันยังไม่ได้ตรวจ bug ตัวนี้

กติกาที่ทำให้วงจรนี้ไม่พัง

| กติกา | เหตุผล |
|---|---|
| คนที่ปิดใบต้องเป็นผู้รายงาน ไม่ใช่คนแก้ | คนแก้มีอคติที่จะเชื่อว่าแก้แล้ว การให้คนอื่นยืนยันคือขั้น Verify ที่แท้จริง |
| ทุกใบที่ปิดแบบ Fixed ต้องมี test ที่จะแดงถ้า bug นี้กลับมา | ไม่งั้นมันจะกลับมาแน่นอน และครั้งหน้าไม่มีใครรู้ตัว |
| Rejected / Duplicate / Deferred ต้องเขียนเหตุผลเสมอ | คนถัดไปจะได้ไม่ต้องเสียเวลาสืบเรื่องเดิมซ้ำ |
| Deferred ต้องมีเงื่อนไขว่าจะกลับมาพิจารณาเมื่อไร | ไม่งั้นมันก็คือการปฏิเสธแบบสุภาพ |
| ใบที่ Reopened เกิน 2 ครั้งต้องยกระดับเป็นการคุยเรื่องสาเหตุราก | แปลว่าไม่มีใครเข้าใจสาเหตุจริง กำลังแก้ที่อาการ |
| ทุกใบต้องมีสถานะและเจ้าของเสมอ | ใบที่ไม่มีเจ้าของคือใบที่ไม่มีใครทำ |

### 9.4.3 เมื่อ bug ที่ปิดไปแล้วกลับมาอีก

การเจออาการเดิมซ้ำหลังปิดใบไปแล้ว เป็นสัญญาณสองชั้นที่ต้องจัดการคนละแบบ

- ชั้นที่เห็นง่าย: ใบนี้จะเดินต่ออย่างไร ซึ่งเป็นเรื่องของกระบวนการติดตาม
- ชั้นที่สำคัญกว่า: ทำไม loop ของเราถึงปล่อยมันผ่านมาได้อีก ซึ่งเป็นเรื่องของคุณภาพ suite

#### เกณฑ์ตัดสินเส้นทาง

```mermaid
flowchart TD
    F["พบอาการเดิมอีกครั้ง<br/>หลังใบเดิมถูกปิดไปแล้ว"] --> Q1{"เป็นอาการเดียวกันจริงไหม<br/>เทียบขั้นตอนทำซ้ำกับใบเดิมทีละขั้น"}
    Q1 -->|"คนละอาการ"| N1["เปิดใบใหม่ตามปกติ<br/>ไม่ต้องอ้างใบเดิม"]
    Q1 -->|"อาการเดียวกัน"| Q2{"สาเหตุรากเดียวกันหรือเปล่า"}
    Q2 -->|"ยังไม่รู้"| I["สืบก่อน อย่าเพิ่งตัดสิน<br/>เปิดใบใหม่ไว้ก่อนพร้อมลิงก์ถึงใบเดิม<br/>แล้วค่อยรวมทีหลังถ้าพบว่าเป็นตัวเดียวกัน"]
    Q2 -->|"คนละสาเหตุ"| N2["เปิดใบใหม่<br/>ลิงก์ว่า related to #เดิม"]
    Q2 -->|"สาเหตุเดิม"| Q3{"ข้าม release ไปแล้วหรือยัง"}
    Q3 -->|"ยังอยู่ในรอบเดิม<br/>ยังไม่ปล่อยให้ผู้ใช้"| R["Reopen ใบเดิม<br/>กลับเข้าสถานะ Assigned"]
    Q3 -->|"ปล่อยไปแล้ว<br/>และปิดรายงานของ release นั้นแล้ว"| N3["เปิดใบใหม่<br/>ลิงก์ว่า regression of #เดิม"]
```

#### สองทางเลือกนี้แลกอะไรกัน

| | Reopen ใบเดิม | เปิดใบใหม่ที่ลิงก์กลับ |
|---|---|---|
| ประวัติการสืบสวน | อยู่ที่เดียว อ่านย้อนได้ครบในใบเดียว | กระจายหลายใบ ต้องตามลิงก์ |
| ความจริงของรายงานราย release | เพี้ยน: ใบที่ปิดไปใน v1.2 จะกลับมาดูเหมือนไม่เคยปิด | ตรง: v1.2 ปิดจริง ส่วน v1.4 มีใบใหม่ |
| ผลต่อตัวชี้วัด | ดันค่า reopen rate ขึ้น (ถูกต้อง ถ้าเป็นการแก้ที่ไม่จบ) | ดันค่า escape rate / regression rate ขึ้น |
| การวางแผนรอบถัดไป | ใบเก่าโผล่กลับเข้า backlog ซึ่งบางทีมมองว่าสับสน | ใบใหม่เข้าคิว triage ตามปกติ |
| เหมาะเมื่อ | ยังไม่ข้าม release และสาเหตุรากเดิม | ข้าม release แล้ว หรือคนละสาเหตุราก |

กฎง่าย ๆ ที่ทีมส่วนใหญ่ใช้คือ ยังไม่ปล่อยของ ให้ reopen ปล่อยไปแล้ว ให้เปิดใบใหม่ที่ลิงก์กลับ
เหตุผลคือรายงานคุณภาพของแต่ละ release ต้องแช่แข็งได้
ถ้าย้อนไปแก้สถานะของใบเก่าได้เรื่อย ๆ จะตอบไม่ได้เลยว่า
"ตอนปล่อย v1.2 เรารู้ตัวไหมว่ามี bug นี้ค้างอยู่"

#### สิ่งที่ต้องทำเสมอ ไม่ว่าจะเลือกทางไหน

การที่ bug ที่ปิดไปแล้วกลับมา แปลว่ากติกา "ทุกใบที่ปิดแบบ Fixed ต้องมี test คุ้มครอง" ถูกละเมิดที่ใดที่หนึ่ง
เราต้องหาให้เจอว่าละเมิดตรงไหน ก่อนจะเริ่มแก้ code

| ทำไมถึงหลุดกลับมาได้ | ต้องแก้ที่ระบบ ไม่ใช่ที่ใบนี้ |
|---|---|
| ปิดใบไปโดยไม่ได้เขียน test เลย | กติกาการปิดใบ บังคับให้แนบชื่อ test ที่คุ้มครอง |
| มี test แต่ตรวจคนละเงื่อนไขกับที่พังจริง | คุณภาพของ assertion ใช้ mutation testing ตรวจย้อน |
| มี test แต่ไม่ได้อยู่ใน suite ที่รันทุก commit | ย้าย test เข้าด่านหลักของ CI |
| test ถูก `skip` หรือ quarantine ค้างไว้ | นโยบาย quarantine ต้องมีวันหมดอายุและมีเจ้าของ |
| แก้แล้วแต่ commit หายตอน merge หรือถูก revert ทับ | เป็นเรื่องของกระบวนการ branch และ release ไม่ใช่เรื่องของ test |

ลำดับการลงมือที่ถูกต้อง

1. เขียนหรือแก้ test ให้แดงกับของที่พังอยู่ตอนนี้ก่อน ถ้าเขียนแล้วมันยังเขียว แปลว่ายังไม่เข้าใจสาเหตุ
2. ค่อยแก้ code จน test เขียว
3. ยืนยันว่า test ตัวนั้นอยู่ในด่านที่รันทุกครั้ง ไม่ใช่ suite ที่รันสัปดาห์ละหน
4. บันทึกสั้น ๆ ว่า loop ปล่อยผ่านมาได้เพราะอะไร แล้วปิดช่องนั้นที่ระบบ

> **ข้อควรระวัง:** ใบเดียวกันที่ถูก reopen เกิน 2 ครั้ง ให้หยุดแก้ที่อาการทันที
> แล้วยกระดับเป็นการคุยเรื่องสาเหตุราก ตัวเลขนี้เป็นสัญญาณที่เชื่อถือได้ว่า
> ไม่มีใครในทีมเข้าใจว่าจริง ๆ แล้วมันพังเพราะอะไร

### 9.5 Triage: การประชุมที่สั้นแต่จำเป็น

รอบละ 15-20 นาที ไล่เฉพาะใบที่สถานะ `New` และตัดสินแค่ 3 อย่าง

1. เป็น bug จริงไหม ถ้าไม่ใช่ ให้ระบุว่าเป็น requirement ใหม่หรือความเข้าใจผิด
2. priority เท่าไร เจ้าของผลิตภัณฑ์เป็นคนตัดสิน
3. ใครเป็นเจ้าของ ต้องได้ชื่อคน ไม่ใช่ชื่อทีม

สิ่งที่ห้ามทำใน triage คือเริ่มดีบักหาสาเหตุตรงนั้น
เพราะจะกินเวลาทั้งห้องเพื่อแก้ใบเดียว ให้บันทึกว่าต้องสืบต่อ แล้วไปใบถัดไป

### 9.6 ตัวเลขที่ใช้ดูสุขภาพของกระบวนการ

| ตัวชี้วัด | สูตร | บอกอะไร |
|---|---|---|
| Defect Removal Efficiency (DRE) | bug ที่เจอก่อนปล่อย ÷ (เจอก่อนปล่อย + เจอหลังปล่อย) × 100 | loop ของเราจับได้กี่ % ก่อนถึงมือผู้ใช้ |
| Escape rate / Leakage | bug ที่ผู้ใช้เจอ ÷ bug ทั้งหมด | สัดส่วนที่หลุดออกไป ยิ่งต่ำยิ่งดี |
| Reopen rate | ใบที่ถูกเปิดใหม่ ÷ ใบที่เคยปิดว่า Fixed | คุณภาพของการแก้และการยืนยันภายในรอบเดียวกัน |
| Regression rate | ใบที่กลับมาอีกหลังปิดและข้าม release แล้ว ÷ ใบที่ปิดทั้งหมด | suite ของเรากันของเก่าไม่ให้พังซ้ำได้ดีแค่ไหน |
| Defect age | เวลาเฉลี่ยตั้งแต่รายงานจนปิด | คิวติดขัดตรงไหน |
| Defect density | จำนวน bug ÷ ขนาดของโมดูล | ส่วนไหนของระบบเสี่ยงที่สุด |

DRE คือ coverage ของ loop ในเชิงกระบวนการ มันตอบคำถามเดียวกับที่ mutation score ตอบในระดับ code
เพียงแต่วัดที่ระดับทีม

> **ข้อควรระวัง:** ใช้ตัวเลขเหล่านี้ดูแนวโน้มของกระบวนการเท่านั้น
> ทันทีที่เอา "จำนวน bug ที่แต่ละคนทำให้เกิด" ไปประเมินคน
> คนจะเลิกรายงาน bug ของตัวเอง และตัวเลขจะสวยขึ้นทั้งที่คุณภาพแย่ลง

## 11. ทดสอบระบบที่มี AI อยู่ข้างใน

ปัญหาพื้นฐานคือ LLM ไม่ deterministic input เดิมอาจได้ output ต่างกัน
`assertEqual(output, "ข้อความที่คาดหวัง")` จึงใช้ไม่ได้

สิ่งที่ยังทดสอบได้แบบเดิมทุกอย่าง

- โครงสร้างของผลลัพธ์ เช่น เป็น JSON ที่ตรง schema ไหม
- ขอบเขต เช่น ไม่มี field ต้องห้ามหลุดออกมา ความยาวอยู่ในเกณฑ์
- พฤติกรรมของระบบรอบ ๆ เช่น timeout, retry, fallback เมื่อ API ล่ม
- ความปลอดภัย เช่น ข้อความที่พยายาม prompt injection ต้องไม่ทำให้ระบบทำสิ่งต้องห้าม
- ต้นทุน เช่น จำนวน token ต่อคำขอไม่เกินเพดาน

สิ่งที่ต้องเปลี่ยนวิธี

```mermaid
flowchart LR
    D["Eval set<br/>ชุดตัวอย่าง input พร้อมเกณฑ์"] --> R["รันหลายครั้ง"] --> S["ให้คะแนนตามเกณฑ์<br/>ไม่ใช่เทียบตรงตัว"] --> TH["ตัดสินที่ค่าเฉลี่ย<br/>เทียบ threshold"]
    TH -->|"ต่ำกว่าเกณฑ์"| F["ถือว่าไม่ผ่าน"]
```

- ใช้ eval set ที่มีตัวอย่างหลากหลาย แทน test case เดี่ยว
- ตัดสินด้วยเกณฑ์ เช่น "ต้องมีข้อมูลครบ 3 อย่าง" ไม่ใช่ข้อความตรงตัว
- ตั้ง threshold เป็นสัดส่วนที่ผ่าน เช่น ≥ 90% ของ eval set
- ระวังการใช้ LLM มาตรวจ LLM ทำได้ แต่ต้องมีชุดที่คนตรวจเองไว้เทียบด้วย ไม่งั้นอคติจะสะสม

อีกด้านหนึ่งคือการทดสอบ code ที่ AI เขียนให้
อันตรายที่สุดคือให้ agent เขียนทั้ง code และ test ในรอบเดียวกัน
เพราะถ้ามันเข้าใจโจทย์ผิด มันจะเข้าใจผิดเหมือนกันทั้งสองไฟล์ และทุกอย่างจะเขียวสวยงาม
วิธีป้องกันคือให้คนกำหนดเกณฑ์ยอมรับก่อน แล้วค่อยให้ agent ทำ
หรืออย่างน้อยคนต้องอ่าน assertion ทุกบรรทัดว่าตรวจสิ่งที่ควรตรวจจริง

## 12. Tester ทำงานร่วมกับ AI อย่างไรให้ได้ผลสูงสุด

เมื่อ AI เขียน code ได้เร็วขึ้นมาก ของที่ต้องตรวจก็เพิ่มตาม
บทบาทของ tester จึงไม่ได้ลดลง แต่ย้ายจุดโฟกัส จากการเขียน test case ทีละใบ
ไปเป็นการออกแบบว่าอะไรคือเกณฑ์ตัดสินว่าถูก ซึ่งเป็นสิ่งที่ AI ให้เราไม่ได้

```mermaid
flowchart LR
    H1["คนกำหนด oracle<br/>อะไรคือ “ถูก” และรู้ได้อย่างไร"] --> AI1["AI ขยาย<br/>แตกกรณี สร้างข้อมูล แปลงเป็น code"]
    AI1 --> H2["คนตรวจ<br/>assertion ตรวจสิ่งที่ควรตรวจจริงไหม"]
    H2 --> A["เข้า automation + CI"]
    A --> H3["คนดูผลที่หลุด<br/>แล้วปรับ oracle ให้แน่ขึ้น"]
    H3 --> H1
```

คำว่า oracle ในวงการทดสอบหมายถึงแหล่งที่บอกว่าผลลัพธ์ที่ถูกต้องคืออะไร
AI ไม่มี oracle ของระบบเรา เพราะมันไม่รู้ว่าธุรกิจนี้ตกลงอะไรกันไว้

### 12.1 แบ่งงานให้ชัด

| งาน | ให้ AI ทำ | คนต้องทำ |
|---|---|---|
| แตก AC เป็น test case เบื้องต้น | ได้ ทำได้ดีมาก ครอบคลุมกว่าที่คนนึกออกเอง | ตัดที่ไม่เกี่ยว เติมกรณีที่ต้องรู้บริบทธุรกิจ |
| ไล่ค่า boundary และ equivalence class | ได้ เป็นงานเชิงกลไก | ยืนยันว่าขอบที่ถูกต้องคือค่าไหน |
| สร้าง test data หลากหลายรูปแบบ | ได้ รวมถึงชื่อภาษาไทย อักขระพิเศษ emoji | ห้ามใช้ข้อมูลจริงของผู้ใช้เด็ดขาด |
| แปลงขั้นตอนทดสอบด้วยมือเป็น Playwright | ได้ ประหยัดเวลามาก | ตรวจว่า locator ที่มันเขียนมีอยู่จริง |
| ร่างรายงาน bug จากบันทึกดิบ | ได้ จัดรูปแบบให้ครบช่อง | ยืนยันข้อเท็จจริงทุกบรรทัดด้วยตาตัวเอง |
| วิเคราะห์ log จำนวนมาก จัดกลุ่มอาการ | ได้ เก่งเรื่องหารูปแบบซ้ำ | ตัดสินว่าสมมติฐานไหนน่าเชื่อ |
| เสนอกรณีที่ทีมอาจมองข้าม | ได้ ไม่มีอคติผูกพันกับ design | ประเมินว่ากรณีนั้นเกิดจริงไหมในบริบทนี้ |
| ตัดสินว่าผลลัพธ์ถูกหรือผิด | ไม่ได้ | คนเท่านั้น |
| จัดลำดับตามความเสี่ยงทางธุรกิจ | ไม่ได้ | คนเท่านั้น |
| ตัดสิน severity/priority | ไม่ได้ | คนเท่านั้น |
| ปิดใบ bug | ไม่ได้ | คนเท่านั้น |
| ตัดสินว่า "ทดสอบพอแล้ว" | ไม่ได้ | คนเท่านั้น |

### 12.2 prompt ที่ใช้ได้จริง 4 แบบ

**1) แตก test case จาก AC**

```
นี่คือ acceptance criteria ของ story:
[วาง AC]

ช่วยแตกเป็น test case โดย:
- ใช้ equivalence partitioning และ boundary value analysis
- แยกเป็น 3 กลุ่ม: happy path / กรณีที่ต้องถูกปฏิเสธ / กรณีขอบ
- ทุก case ต้องระบุว่ามาจาก AC ข้อไหน
- ท้ายสุดให้ลิสต์ "สิ่งที่ AC นี้ยังไม่ได้ระบุ จึงทดสอบไม่ได้" แยกออกมา
```

บรรทัดสุดท้ายมีค่าที่สุด มันเปลี่ยน AI จากเครื่องผลิต test case
เป็นเครื่องมือหาช่องโหว่ใน requirement

**2) หากรณีที่ทีมมองข้าม**

```
นี่คือ test case ที่เรามีอยู่แล้ว: [วางรายการ]
นี่คือ code ของฟังก์ชัน: [วาง code]

อะไรคือกรณีที่ code นี้จะทำงานผิดแต่ test ชุดนี้จับไม่ได้
เรียงตามความน่าจะเกิดในการใช้งานจริง และอธิบายว่าทำไม test เดิมถึงจับไม่ได้
```

**3) แปลงบันทึกดิบเป็นรายงาน bug**

```
นี่คือบันทึกดิบจากการทดสอบ: [วาง]
นี่คือแม่แบบรายงานของเรา: [วางแม่แบบในหัวข้อ 9.2]

จัดให้อยู่ในแม่แบบ โดย:
- ถ้าข้อมูลช่องไหนไม่มีในบันทึก ให้เขียนว่า "ยังไม่มีข้อมูล" ห้ามเดา
- แยก "ข้อเท็จจริงที่สังเกตได้" ออกจาก "การคาดเดาสาเหตุ" ให้ชัด
```

ข้อห้ามเดาสำคัญมาก เพราะรายงาน bug ที่มีรายละเอียดที่ถูกแต่งขึ้น
จะทำให้ dev ไล่ผิดทางและเสียความเชื่อถือใน tester ไปด้วย

**4) วิเคราะห์ flaky test**

```
test นี้แดง 3 ใน 20 ครั้งบน CI แต่เขียวตลอดในเครื่อง
นี่คือ test: [วาง]  นี่คือ log ของรอบที่แดง: [วาง]

ระบุสาเหตุที่เป็นไปได้ 3 อันดับ เรียงตามหลักฐานที่มี
และบอกว่าจะยืนยันหรือตัดแต่ละข้อออกได้ด้วยการวัดอะไร
ห้ามเสนอให้ใส่ retry หรือ sleep
```

### 12.3 กับดักที่ต้องระวัง

```mermaid
flowchart TD
    T1["ให้ agent เขียนทั้ง code และ test<br/>ในรอบเดียวกัน"] --> D1["เข้าใจโจทย์ผิดเหมือนกันทั้งสองไฟล์<br/>ทุกอย่างเขียวสวยงามแต่ผิดหมด"]
    T2["สั่งว่า “ทำให้ test ผ่าน”"] --> D2["agent แก้ test แทนที่จะแก้ code<br/>ตาข่ายนิรภัยหายไปเงียบ ๆ"]
    T3["รับ test ที่ generate มาโดยไม่อ่าน assertion"] --> D3["ได้ coverage สูงแต่ mutation score ต่ำ"]
    T4["ให้ AI สรุปว่า “ระบบพร้อมปล่อยแล้ว”"] --> D4["ไม่มีใครรับผิดชอบการตัดสินใจนั้น"]
    T5["วางข้อมูลผู้ใช้จริงลง prompt"] --> D5["ข้อมูลส่วนบุคคลรั่วออกนอกองค์กร"]
```

มาตรการที่ตอบกับดักแต่ละข้อ

- ข้อ 1: ให้คนเขียนหรืออนุมัติ AC และ assertion ก่อน แล้วค่อยให้ agent เขียน implementation
  หรืออย่างน้อยให้คนละรอบหรือคนละ context กัน
- ข้อ 2: ใส่ข้อห้ามลงใน prompt และใน `AGENTS.md` ว่าห้ามแก้ไฟล์ test
  แล้วตรวจด้วย `git diff --stat` ทุกครั้งก่อน commit
- ข้อ 3: อ่าน assertion ทุกบรรทัด และใช้ mutation testing ตรวจซ้ำ
- ข้อ 4: การตัดสินใจ go/no-go ต้องมีชื่อคนกำกับเสมอ ตาม RACI
- ข้อ 5: ใช้ข้อมูลสังเคราะห์เท่านั้น และตรวจว่าไม่มี secret ตามกติกาข้อ 3 ของวิชา

### 12.4 วิธีวัดว่าการใช้ AI ได้ผลจริง

อย่าวัดที่ "เขียน test ได้กี่ตัว" เพราะจำนวน test ไม่ใช่คุณภาพ ให้ดูตัวเลขที่มีความหมายแทน

| ก่อนใช้ AI | หลังใช้ AI | ตีความ |
|---|---|---|
| escape rate | ลดลง | จับได้เร็วขึ้นจริง |
| mutation score | สูงขึ้น | test มีคุณภาพขึ้น ไม่ใช่แค่เยอะขึ้น |
| จำนวน test | เพิ่มขึ้นมาก แต่ escape rate เท่าเดิม | ระวัง: ได้ test ที่ไม่ตรวจอะไร |
| เวลา review test | เพิ่มขึ้นจนกลายเป็นคอขวด | ระวัง: ต้องลดปริมาณลงและเน้นคุณภาพ |

> **กรณีตัวอย่าง**
> ทักษะของ tester ที่มีมูลค่าสูงขึ้นในยุคนี้คือการตั้งคำถามที่ทำให้ความคลุมเครือปรากฏ
> เพราะทั้งมนุษย์และ AI สร้าง code จาก requirement ที่กำกวมได้เร็วพอ ๆ กัน
> แต่คนที่ถามว่า "ถ้าสองคนกดพร้อมกันเป๊ะ ๆ จะเกิดอะไร" ยังหายากเหมือนเดิม

## 13. Checklist ก่อนบอกว่า "test พอแล้ว"

- [ ] ทุก business rule ที่เขียนใน spec มี test อย่างน้อย 1 ตัวที่จะแดงถ้าลบ rule นั้นทิ้ง
- [ ] มี test ของกรณีที่ต้องล้มเหลว ไม่ใช่เฉพาะ happy path
- [ ] ค่าที่ขอบถูกทดสอบ ไม่ใช่แค่ค่ากลาง ๆ
- [ ] test ทั้ง suite รันได้จบเร็วพอที่จะรันทุกครั้งที่แก้ code
- [ ] สลับลำดับ test แล้วยังเขียว
- [ ] รัน 10 ครั้งติดกันแล้วเขียวทั้ง 10 ครั้ง
- [ ] ลองแก้ code ให้ผิดโดยตั้งใจ 1 จุด แล้วมี test แดงจริง
- [ ] ไม่มี test ที่ถูก skip ค้างไว้โดยไม่มีเหตุผลกำกับ
- [ ] CI รัน test ชุดเดียวกับที่รันในเครื่อง และได้ผลเหมือนกัน

ข้อที่ 7 คือ mutation testing แบบทำมือ และเป็นข้อที่ให้ข้อมูลมากที่สุดในเวลาที่น้อยที่สุด
